# ADR 0004 — Persistencia PostGIS: SQL plano con `psycopg`, `MultiPolygon` fijo, sin repository port todavía

- Estado: aceptada
- Fecha: 2026-10-15

## Contexto

La historia 0003 pide un esquema PostGIS y migraciones para `parcel` y `building`, y deja seis preguntas abiertas explícitas para el arquitecto: herramienta de migraciones, tipo de columna PostGIS para `Geometry`, si hace falta ya un `ParcelRepositoryPort`, librería de acceso a datos (con o sin ORM), imagen de PostGIS para `infra/docker-compose.yml`, y si `Provenance` se aplana por tabla o se extrae a un tipo compuesto reutilizable.

Hoy no hay ningún driver de base de datos instalado (`pyproject.toml` solo trae `requests`, `fastapi`, `uvicorn` como runtime, más `httpx`/`pytest`/`mypy`/`ruff`/`import-linter` en dev). `domain/geometry.py` fija `Geometry.rings: tuple[Ring, ...]` sin distinguir "una pieza" de "varias piezas": un edificio de un solo cuerpo y uno de varios se representan con el mismo tipo, solo cambia `len(rings)`. `domain/provenance.py` es ya un value object compartido (ADR 0002) con cuatro campos (`source`, `url`, `retrieved_at`, `license`), y `Parcel`/`Building` lo incluyen por composición. No existe todavía ningún caso de uso en `application/` que necesite leer o escribir `Parcel`/`Building` en una base de datos: `GenerateParcelReportUseCase` llama directamente a `ParcelGeometryPort`/`BuildingGeometryPort` contra Catastro.

## Decisión

1. **Migraciones: SQL plano con un runner propio, sin Alembic ni ningún framework de migraciones de terceros.** `src/parcel_intel/adapters/postgis/migrations/` contiene pares de ficheros `NNNN_<nombre>.up.sql` / `NNNN_<nombre>.down.sql` (empezando por `0001_create_parcel` y `0002_create_building`). `src/parcel_intel/adapters/postgis/migrate.py` es un script con `up`/`down`/`status` que registra lo aplicado en una tabla `schema_migrations` (versión + fecha), y se invoca con `uv run python -m parcel_intel.adapters.postgis.migrate up` — este comando se documenta literalmente en `CLAUDE.md`. No es una violación de "`cli/` es el único composition root": el runner no instancia adapters para inyectarlos en un caso de uso, solo ejecuta DDL contra la base de datos; es infraestructura de arranque, igual que `infra/docker-compose.yml`, no wiring de aplicación.

2. **Columna de geometría: `geometry(MultiPolygon, 25830)` fija**, igual para `parcel.geometry` y `building.geometry` — no genérica (`geometry(Geometry, 25830)`) ni fija a `Polygon`. El mapeo del adapter serializa *siempre* como `MULTIPOLYGON(((...)), ((...)), ...)`, con cada anillo de `Geometry.rings` como un elemento de la lista, sea `len(rings) == 1` o más. Esto da una correspondencia 1:1 sin casos especiales entre "una pieza" y "multi-parte" (exactamente el mismo código de mapeo sirve para ambos), y añade una restricción real a nivel de esquema (un `Point` o `LineString` insertado por error no pasa el typmod), cosa que la columna genérica no ofrece.

3. **No se introduce `ParcelRepositoryPort` ni ningún otro port de persistencia en `ports/` en esta historia, ni wiring desde `application/`.** Ningún caso de uso real lo necesita todavía (confirmado arriba). El adapter expone una clase concreta `PostgisParcelRepository` en `src/parcel_intel/adapters/postgis/repository.py`, con métodos nombrados por capacidad previendo el futuro port (`save_parcel`, `get_parcel`, `save_buildings`, `get_buildings_for_parcel`) para que extraer el `Protocol` el día que exista un consumidor real sea solo mover firmas, no rediseñar. El test de integración del Bloque 3 instancia y llama a esta clase directamente, no a través de un port — igual que los tests de `CatastroAdapter` ya instancian el adapter concreto directamente.

4. **Driver: `psycopg` (v3), sin ORM, SQL parametrizado escrito a mano.** Se añade como dependencia de runtime (`psycopg[binary]>=3.1`, extra `binary` para no exigir `libpq-dev` en cada máquina de desarrollo). El mapeo fila↔dominio se hace con `TypedDict` para las filas crudas (siguiendo la lección ya registrada sobre `TypedDict` en los bordes de parsing) y construcción manual de WKT/EWKT para la geometría (`ST_GeomFromText(..., 25830)` al escribir, `ST_AsText(geometry)` + `ST_SRID(geometry)` al leer). Se descarta SQLAlchemy (ORM o Core) y Alembic.

5. **Imagen Docker: `postgis/postgis:16-3.4`** (variante Debian, no `-alpine`), con el tag fijado explícitamente (nunca `latest`) en `infra/docker-compose.yml`. PostgreSQL 16 + PostGIS 3.4, mantenida por el proyecto PostGIS, sin asumir límites de ningún proveedor cloud gestionado — coherente con el servidor casero de producción.

6. **`Provenance` se aplana en columnas propias por tabla** (`provenance_source`, `provenance_url`, `provenance_retrieved_at`, `provenance_license`), tal como ya lo describe el criterio de aceptación de la historia. No se extrae todavía a un tipo compuesto de PostgreSQL ni a una tabla `provenance` separada.

## Alternativas consideradas

- **Alembic** (con o sin SQLAlchemy Core para las migraciones): rechazada. Alembic depende obligatoriamente de SQLAlchemy incluso si cada migración se escribe en SQL plano (`op.execute(...)`), lo que mete un segundo paquete de terceros solo para versionar DDL de dos tablas, y crea una tentación natural de deslizarse hacia SQLAlchemy Core/ORM para las consultas más adelante, mezclando dos decisiones (herramienta de migraciones vs. librería de acceso a datos) que conviene mantener independientes. Para dos tablas, un runner de ~80 líneas sobre `schema_migrations` cubre los criterios de aceptación (aplicar desde cero, revertir la última, no duplicar en aplicaciones repetidas) sin dependencia nueva.
- **`geometry(Geometry, 25830)` genérico**: rechazada. Es viable (la geometría de PostGIS más laxa) pero renuncia a una restricción de esquema real sin ganar nada a cambio: el mapeo de ida y vuelta es exactamente el mismo código si se fija el serializado a `MULTIPOLYGON` siempre. La única razón para preferir el tipo genérico sería admitir formas que el dominio no modela (huecos, líneas, puntos) — y el dominio explícitamente no las admite.
- **`geometry(Polygon, 25830)` fijo**: rechazada. Rompería en el primer edificio con `len(rings) > 1` (exactamente el caso multi-parte que ya causó un bug de producción documentado en `docs/lessons/LESSONS.md`), obligando a una tabla auxiliar o a degradar la geometría a "solo el primer anillo" — ambas peores que `MultiPolygon` fijo.
- **Crear `ParcelRepositoryPort` ya, con wiring mínimo en `application/`**: rechazada por ahora. No hay ningún caso de uso que lo necesite hoy; introducirlo sin un consumidor real repetiría el patrón ya señalado como lección en este mismo proyecto ("no diseñar para requisitos hipotéticos") y en el ADR 0002 (los ports se crean cuando hay una capacidad real que cubrir, no por anticipación). El coste de añadirlo después es bajo porque `PostgisParcelRepository` ya se nombra por capacidad.
- **`psycopg2` en vez de `psycopg` (v3)**: rechazada. `psycopg` v3 trae tipado inline (PEP 561) sin depender de un paquete de stubs de terceros (`types-psycopg2`), lo que encaja mejor con la exigencia de `CLAUDE.md` de mypy estricto siempre en verde. `psycopg2` sigue siendo la opción más probada en producción, pero su superficie de tipado es más débil.
- **`asyncpg`**: rechazada. Nada en el stack actual (`application/`, `api/main.py` tal como está) es asíncrono; introducir un driver async-only solo para este adapter obligaría a decidir prematuramente si el resto del motor se vuelve async, una decisión que ninguna historia ha pedido todavía.
- **SQLAlchemy ORM**: rechazada. Iría contra el patrón ya establecido en `adapters/catastro/` (parsing manual a `TypedDict` y dataclasses, sin capa de mapeo declarativa) y añadiría una capa de metaclases/sesiones cuyo tipado estricto con mypy es notoriamente más frágil que SQL parametrizado + `TypedDict`.
- **`provenance` como tipo compuesto de PostgreSQL o tabla separada**: rechazada por ahora. Con dos tablas consumidoras, un `CREATE TYPE ... AS (...)` o una tabla `provenance` con FKs añade friction de migraciones (alterar un tipo compuesto usado como columna exige recrearlo) y de mapeo (`psycopg` representa tipos compuestos como tuplas por defecto, exigiendo adaptadores propios) desproporcionada frente al beneficio en n=2. Cuando `Observation`, `LayerFeature`, `Norm` y `BulletinEntry` tengan su propia tabla (historias futuras) y se repita la misma aplanada cuatro veces más, ese es el punto natural para revisitar esta decisión — se señala aquí para no perderlo de vista, pero no bloquea esta historia.
- **Imagen PostGIS `-alpine` o `latest`**: rechazada. La variante Alpine ha tenido históricamente more fricción de compatibilidad con extensiones PostGIS/locale; `latest` rompe la reproducibilidad exigida por el criterio de aceptación "parar, eliminar y volver a levantar deja el mismo estado" en cuanto la imagen cambie de versión entre ejecuciones.

## Consecuencias

- Nueva dependencia de runtime: `psycopg[binary]>=3.1` en `pyproject.toml` (`[project.dependencies]`), y nuevo servicio `db` en `infra/docker-compose.yml` con la imagen `postgis/postgis:16-3.4`.
- `CLAUDE.md` gana una línea en "Comandos" documentando literalmente el runner de migraciones (`uv run python -m parcel_intel.adapters.postgis.migrate up`), conforme al criterio de aceptación de la historia y a la lección ya registrada sobre comandos que deben ejecutarse tal cual están escritos.
- El adapter de mapeo (`adapters/postgis/mapping.py` o equivalente) debe cerrar explícitamente los anillos antes de construir WKT si `Geometry.rings` no garantiza que el primer y último punto coincidan — el dominio no impone esa invariante, así que el borde adapter↔SQL es responsable de no producir WKT inválido. Se señala aquí para que no se pierda, en la línea de la lección sobre tratar con sospecha la geometría reimplementada a mano.
- El `CHECK` de `building.origin` (restringido a `catastro`/`detected`) duplica en SQL los valores del `Literal` de `domain/building.py`. Si `BuildingOrigin` gana un tercer valor en el futuro, hace falta una migración nueva para ampliar el `CHECK` — riesgo de sincronización menor pero real, a vigilar cuando aparezca el adapter de detección de imagen.
- **Coste de salida del proveedor (PostgreSQL/PostGIS):** medio, y contenido a un único directorio. Todo el SQL (DDL de las migraciones, DML del repositorio, funciones espaciales `ST_GeomFromText`/`ST_AsText`/`ST_SRID`) vive exclusivamente en `adapters/postgis/`; `domain/`, `ports/`, `application/` y `cli/`/`api/` no saben que la base de datos es PostgreSQL. Migrar a otro motor espacial (p. ej. SQLite+SpatiaLite para un despliegue más ligero, o un Postgres gestionado en la nube si el servidor casero deja de bastar) exige reescribir ese directorio y las migraciones, pero cero cambios en el resto del motor — es exactamente el punto de la frontera hexagonal. Cambiar solo de *driver* (p. ej. de `psycopg` a otro cliente Postgres) es aún más barato: queda contenido a `connection.py`/`repository.py`, sin tocar el SQL de las migraciones.
- Riesgo residual señalado explícitamente para revisitar, no para esta historia: la aplanación de `Provenance` (punto 6) y el `ParcelRepositoryPort` diferido (punto 3) son las dos decisiones de esta ADR con mayor probabilidad de necesitar revisión cuando lleguen `observation`/`rule`/`bulletin_entry` o el primer caso de uso real de lectura/escritura contra PostGIS.
